# 三家外部厂商虚拟机兜底回收

## 执行周期

独立于本地 OpenStack 残留清理任务，外部厂商一、二、三各自每 5 分钟巡查一次，在对应分钟的第 0、5、10 秒错峰执行。某家厂商不可用不会阻塞另两家。厂商二 IP 台账每 20 秒核对，厂商三 VMID 台账每分钟核对。

## 自动回收条件

本任务处理 **MP 已完成删除而厂商侧仍存在** 的虚拟机，同时核对 **厂商 VM 已消失而本地台账仍持有资源/IP** 的记录。不把正在创建、停止但未删除、异常未完成删除或未关联 MP 的虚拟机作为可直接删除的资源。

2026-11-28 新增独立的 `vendor_scene_delete_retry` 任务，每分钟检查“前台实例已关闭、场景 DELETE/ABNORMAL”的记录，重入正常场景删除流程；与本任务的已关闭场景残留资源巡查分别运行。单场景两次自动重试至少间隔 5 分钟、每轮最多 8 个，使用持久化领取记录避免多 MP 实例重复排队。详见 `vendor_reclaim_recovery_20261128.md`。

- MP 场景为已删除，场景和节点均为 DELETE/OVER；综合场景实例已关闭。默认关闭时间至少 10 分钟。
- 原节点为 MP 管理的虚拟机，不是外部引用；有历史资源标识，或可由原场景、节点的厂商台账恢复标识。
- 没有仍未关闭的同厂商资源引用，候选的历史归属明确。
- 厂商清单成功且完整，实际资源存在，唯一名称与身份匹配。厂商一、二使用厂商分配的 UUID 和 MP 创建名称；厂商二有原地址台账时同时校验其归属。厂商三必须具有持久化 VMID 和原始唯一创建名称的台账，不根据旧 VMID 或名称前缀推断归属。
- 持久化领取回收任务后重新检查 MP 关闭状态；厂商适配器再次确认真实资源身份，再调用现有回收流程。不会执行本地 OpenStack 强制删除接口。

厂商三无原始身份台账的历史重复 VMID、名称变化、人工创建资源、仍有活动场景引用等不自动删除。清单不完整或接口异常时跳过该轮。回收失败保留关联，后续巡查重试；若完整资源清单确认原 UUID/VMID 和原名称均已消失，则补记回收确认。同一实例领取后有持久化防重；异常中断时保留两小时的领取保护期。

当前实现不再直接跳过清单中已不存在的历史 UUID/VMID：先复核原场景已关闭、没有活跃场景使用，再调用对应适配器核对遗留台账。厂商二的 USED/RELEASING/LEGACY 地址可在确认 VM 消失、无其他地址占用且检测无应答后重入 FREE；若 IP 仍有占用则隔离并由 20 秒地址任务继续核对。厂商一创建台账、厂商三 VMID 台账也会对已消失资源结案。该分支不重复发送删除接口，汇总日志另列 `已消失资源台账结案` 数量，避免把台账收尾统计为新删除的 VM。

正常失败结果的重试间隔为 2 分钟，配合每 5 分钟巡查；已经领取且结果不明的 RECLAIMING 记录仍保留两小时的防重窗口。

## 默认配置

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| XD_VENDOR_RECLAIM_ENABLED | true | 兜底回收总开关 |
| XD_VENDOR_RECLAIM_CLOSED_GRACE_MINUTES | 10 | MP 完成关闭至允许巡查回收的最短时间 |
| XD_VENDOR_RECLAIM_MAX_PER_RUN | 20 | 每家厂商每轮最多尝试回收的资源数 |

每轮先扫描全部符合 MP 关闭条件的历史引用，按未尝试及较早尝试优先处理。每个厂商独立执行，超过轮次预算或数量限制的残留留待下一轮。

## 审计与上线

新增 MySQL/DM 迁移 `V202611261100__vendor_vm_reclaim.sql`，记录每项资源的归属、回收状态、尝试次数和更新时间。可通过以下查询核对任务执行结果：

```sql
SELECT vendor, status, COUNT(*) FROM mp_vendor_vm_reclaim
GROUP BY vendor, status;
```

状态含义：`RECLAIMING` 正在处理，`VERIFY_PENDING` 结果待确认，`CONFIRMED` 已确认回收，`SKIPPED` 领取后发现不再满足关闭条件。未建立回收记录的候选也可能因身份不明确而跳过，具体查看厂商兜底回收汇总日志。

上线须随 MP 应用对应迁移；未连接现场厂商或实际执行删除的本地测试不代替现场验收。
